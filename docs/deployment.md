# Deployment

How Game's Up runs in production: the Docker Compose stack, the SSH deploy script, and the data it keeps. Local development is in [development.md](development.md).

## Production Docker

Production runs `compose.server.yml` (tracked) in a checkout on the server, with secrets and the public origin in an untracked `.env` beside it. A value that only one host needs goes in an untracked `compose.override.yml`, which the deploy adds when it exists. The public site is served by the server's shared nginx container, which reaches the app container (`game-is-up-api`) by name over the external `nginx_default` network; no port is published. Its site file is the tracked `nginx.server.conf`, installed as `gamesup.conf`. Cloudflare terminates HTTPS in front of it: the site restores the visitor's address from `CF-Connecting-IP` for Cloudflare's published ranges and sends `X-Forwarded-Proto https`, and the API's rate limits rely on that address. When Cloudflare changes its ranges (https://www.cloudflare.com/ips/), update the `set_real_ip_from` list.

To set up a server checkout:

1. Copy `.env.server.example` to `.env` and set `POSTGRES_PASSWORD`, `SESSION_SECRET`, `CLIENT_ORIGIN` (the public URL) and `DISCORD_CALLBACK_URL` (`${CLIENT_ORIGIN}/api/auth/discord/callback`). Compose refuses to start without them.
2. If Play composer calls should create a temporary Discord space in the Game's Up Discord server, also set `DISCORD_SERVER_ID` to that server's guild id.
3. Leave `VITE_API_BASE_URL` empty, so the web app calls the API on the same origin.
4. Make sure the `nginx_default` network and the nginx container exist, then deploy (below). For a first manual start: `docker compose -f compose.server.yml up --build -d`.

### Deploying

Deploy from your local workspace with `npm run deploy:prod`. The script is generated by devkit (`npm exec devkit-init`, configured in the `deploy` block of `devkit.config.mjs`), and its target comes from `.env`, which it loads: `DEPLOY_SSH_HOST`, `DEPLOY_REPO_PATH` and `DEPLOY_NGINX_SITES_DIR` (the server's absolute nginx sites folder, for example `/srv/nginx/sites`; required because this app installs a site file, and kept only in `.env` because it is a real server path), and optionally `DEPLOY_SSH_PORT` (22), `DEPLOY_BACKUP_DIR` (`.backups` in the server checkout) and `DEPLOY_NGINX_CONTAINER` (`nginx`). It uses your normal SSH config, so a host alias works.

It refuses before reaching the server unless the local tree is clean and `HEAD` is exactly a freshly fetched `origin/main`, then runs `npm run validate` (`--skip-validate` skips it). On the server, in order, it:

1. refuses a checkout with tracked changes;
2. dumps the database and verifies the dump (see Backup below);
3. fast-forwards the checkout to `main`, and stops unless it landed on the commit validated locally;
4. runs `docker compose up --build -d --wait`, passing the commit and `version` from `package.json` as the images' OCI labels, and stops with the service status and recent logs if a service is not healthy within five minutes;
5. installs `nginx.server.conf` if it changed: the previous file is kept in `site-backups/`, the new one must pass `nginx -t`, and nginx reloads; a failed test restores the previous file and fails the deploy;
6. prunes dangling images (`--no-prune` or `DEPLOY_PRUNE=0` skips it).

`--dry-run` runs the local checks and prints the server script without running anything.

Production runs one image, built from the root `Dockerfile` (DIST-12): the API, which also serves the built web app, as the unprivileged `node` user. Its start command, `npm run start:prod`, applies pending migrations with `prisma migrate deploy` and then starts the API. Use `db:migrate` to create migrations during development; production applies them on the next start after a deploy.

The API serves the web app on the same origin, so `VITE_API_BASE_URL` stays empty. Hashed files under `/assets/` are cached for a year as immutable; the app shell and the files update checks read (`index.html`, `sw.js`, `registerSW.js`, `manifest.webmanifest`, `build-id.json`) are sent `no-store`, and any other path gets the app shell, so installed PWAs see a new build at once. When the web app is built with `VITE_API_BASE_URL=` empty, client auth flows still construct absolute OAuth entry URLs so redirects stay stable behind the reverse proxy.

Both services set `no-new-privileges` and memory and process limits (CTR-7). The defaults in `compose.server.yml` (512 MB each; 128 processes for the app, 256 for the database) sit well above measured use and can be changed with `API_MEM_LIMIT`, `API_PIDS_LIMIT`, `DB_MEM_LIMIT` and `DB_PIDS_LIMIT` in `.env`.

For Cloudflare-backed deployments, no cache purge is needed: nginx serves the app-shell URLs (`/`, `/index.html`, `/sw.js`, `/registerSW.js`, `/manifest.webmanifest`) with `Cache-Control: no-store`, so the edge never caches them (`cf-cache-status: BYPASS`/`DYNAMIC`) and installed PWAs pick up new builds on their next service-worker check. Hashed assets stay long-lived and immutable. If a Cloudflare-level cache rule (for example "Cache Everything") is ever added, it must exclude those shell URLs or app updates will stall for installed clients.

### Changing the database password on an existing deployment

The Postgres image reads `POSTGRES_PASSWORD` only when it creates an empty data volume. On a running deployment, changing the value in `.env` does not change the database password, and the API then fails to connect. Change the role's password inside the database first, then the configuration. Run these in the server checkout:

1. Generate a URL-safe value, for example with `openssl rand -hex 32`.
2. Set it on the database role. `\password` prompts for the value, so it stays out of shell history and the process list:

```bash
docker compose -f compose.server.yml exec db psql -U postgres -d game_is_up -c '\password postgres'
```

3. Put the same value in the server's `.env` as `POSTGRES_PASSWORD`.
4. Recreate the containers with `docker compose -f compose.server.yml up -d`, then confirm the API reports healthy with `docker compose -f compose.server.yml ps`.

Between steps 2 and 4 the API cannot open new database connections, so do the steps together.

The same order applies when moving an existing deployment off the old built-in default.

## Data and privacy

Game's Up collects no crash reports. When `UMAMI_SCRIPT_URL` and `UMAMI_WEBSITE_ID` are set, the web app counts page views with the self-hosted, cookieless Umami (`apps/web/src/lib/analytics.ts`): it sends the page address with its query, hash and any identifying path segment removed, only the app's fixed page titles, the referrer without its query, and the screen size and language, and it honours Do Not Track. Nothing else leaves the server. The public privacy policy is `apps/web/src/pages/PrivacyPage.tsx`, at `/privacy`; keep it in step with this section.

### What is stored

Account and product data lives in the PostgreSQL database in the `postgres-data` volume. Sessions are signed cookies and are not stored on the server. The API also keeps a disk cache of game covers and Discord avatars under the container's temporary directory (`game-is-up/game-media-cache/`), which is lost when the container is recreated; avatars are re-fetched after 7 days.

- **Profile:** the Discord user id, handle, display name and avatar URL from Discord sign-in (sign-in does not request the email address, and none is stored), plus the timezone, bio and usual-availability note the user sets.
- **Linked accounts:** the Discord OAuth access and refresh tokens, the user's Discord server memberships, and, when linked, the Steam account id.
- **Library and social graph:** games, platforms and interests; friends, blocks, mutes and friends lists; discovery server preferences.
- **Calls to play:** each call, its audience and games, responses, participant invitations, notifications, and the ids of the Discord messages the bot sent for it.
- **Discord activity:** for signed-up users only, the games the bot sees them playing in a server it shares with them, kept against their account and used for library suggestions, the friends' trending row and auto-play prompts. A user who signs up later has no history from before sign-up. Everyone else the bot sees, including members who never signed up, is counted only anonymously: per game, per server and per UTC day, with no Discord id or other identifier (the `DiscordGameActivityDaily` table, for trending views). Since this change was deployed, the count is the number of presence updates seen, which measures activity, not people. Rows backfilled once from the old per-person records instead count distinct people last seen playing that day, and are marked as such.
- **Discord bot state:** composer drafts, invite attribution, and reports.

### On the user's device

The web app keeps the chosen theme in the browser's local storage, and its service worker caches the app shell and up to 500 game covers and avatars for 30 days.

### Retention

- Bot DM chains for a call to play are deleted 12 hours after the call's window ends; temporary Discord spaces 12 hours after their last activity.
- Discord composer drafts expire after 24 hours.
- Everything else is kept until the account is deleted. The anonymous per-game daily counts hold no identifiers, belong to no account, and are kept.

### Account deletion

There is no self-service account deletion in the app yet. A user asks the operator, who deletes the user's row in the `User` table. This procedure has not yet been tried on a real database. Going by the schema:

- Records linked to the account (profile, linked accounts and tokens, library, friends, blocks, mutes, lists, calls to play, responses, notifications, activity observations, observed games, drafts, reports) are removed with it by cascading deletes.
- Invite attributions the user sent are kept, with the inviter's account cleared but their Discord user id kept.
- Other users' notifications and catalog aliases that name the user keep a dangling id.
- Discord messages the bot already delivered stay in Discord. Because their tracking rows are deleted with the account, the retention sweep no longer cleans them up.

### Export

There is no data export.

### Backup

Every deploy first takes a database dump into `.backups/pre-deploy-<UTC time>-<commit>.sql.gz` in the server checkout, before any migration can run. The dump must pass a gzip integrity check and end with pg_dump's completion trailer, or it is deleted and the deploy stops. The backup folder is private to the deploy user (700) and each dump is 600, since dumps hold every user's data. The newest ten are kept. Skip it with `--skip-backup` (or `DEPLOY_BACKUP=0`) only when you have taken a dump another way. To restore one into the running database: `gzip -dc .backups/<file> | docker compose -f compose.server.yml exec -T db psql -U postgres -d game_is_up` (into an empty database, or after dropping and recreating it).

Beyond those dumps, backup is the host's: the server is a virtual machine whose whole disk, including the `postgres-data` volume, is backed up by the hypervisor (Proxmox whole-machine backups). The operator, who runs the server, is responsible for those backups and for restoring from them. A restore has not yet been tried. Backups hold the same personal data and tokens as the live database and need the same protection.
