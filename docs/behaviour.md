# Product behaviour

How Game's Up behaves for users, area by area. Setup steps are in [development.md](development.md); the internal design behind these behaviours is in [ARCHITECTURE.md](../ARCHITECTURE.md).

## Web app

The dashboard uses route-backed tabs, so the main views live at `/` for Home, `/network`, `/friends`, `/library`, `/discovery`, and `/play`. Admin users also get a `/debug` tab for bot, DM lifecycle simulator, prompt, notification, and invite-attribution diagnostics. Discord sign-in preserves same-origin return URLs so a user can authenticate and land back on the view they started from, and invite links can land on a dedicated `/invite` route before handing off into Discord OAuth.

The Play tab keeps both active and recently ended calls to play visible across the viewer's network, including targeted friend-only, friends-list, or selected-server calls that explicitly include that viewer. By default, the Play page filters those lists to calls that apply to the viewer's current library, but each section can be switched to show all visible calls.

Interested players can choose "I'll be late" on the call's detail page or Discord invite and enter an optional delay in minutes. Leave it blank when unsure, or use "Update delay" to revise it later. Estimates appear alongside the player's response and in updates to the creator and other invited players who have not declined. Saving the same estimate again does not send another notification.

Organizers can allow accepted participants to invite their own friends, one at a time. This is enabled by default and can be turned off in the web composer or the bot composer's review step. Participants use "Invite a friend" on the call's web detail page or their Discord invitation. Friends must have a matching playable game and respect existing blocks, mutes, and schedule eligibility. Turning invitations off prevents new additions; it does not remove friends already invited, and organizer edits retain those additions. Some existing calls may ask participants to accept again after upgrading, before they can invite friends.

The Friends page also supports reusable friends lists so creators can save common audience groups and target those saved lists directly from the Play composer.

Server admins can place a persistent Game's Up hub with `/setup-ctp-post`. Its buttons let people join, send out a call to play, manage My games and My friends privately in Discord, or open the App. Joining uses the existing Discord sign-in and web onboarding with server context; new users are encouraged to set up games and friends in the App. Linked users can also start with an empty library or no friends directly in Discord. My games supports catalog search, platforms, play interest, editing, and confirmed removal. My friends supports eligible discovery, one-way app follows, and reusable friends lists with names and paged membership editing. These follows do not change Discord friendships. Each panel has an App shortcut to the corresponding page. Re-running the setup command refreshes or moves the same tracked post; the existing optional channel lock still works.

The Discord composer's title, note, and Friend invites actions share their step's navigation row so they stay visible alongside dropdowns. Discord determines native button widths. Errors appear in separate red-accented embeds above the composer or management panel, while successful changes have green notices. Stale forms ask you to refresh instead of overwriting newer settings.

Signed-in dashboard sessions also keep themselves fresh through a same-origin Server-Sent Events invalidation stream. When impactful shared state changes land on the API, open tabs can automatically reload discovery, play, library, network, and session data without a polling loop.

## Play intent model

Users are not limited to one active call to play. They can keep multiple active calls as long as those availability windows do not overlap. Each call can target:

- a selected subset of 1 to 5 games

Calls to play can also control who sees them:

- explicit friends only
- the broader discovery audience formed by opted-in shared Discord servers, plus friends
- a specific hand-picked set of friends
- one or more specific opted-in Discord servers within that broader discovery audience

Calls to play can start immediately or be scheduled for later, and they remain visible until the configured end time. If a currently active call starts applying to someone later because their library changes, the app will surface it retroactively and backfill the missing invite or go-time reminder.

In the web composer, choosing "Schedule later" suggests a start one hour ahead, rounded to the nearest 15 minutes. Exact halfway points round later. The default one-hour duration and manually selected times are unchanged.

The Play view keeps recently ended calls to play visible for a short closed-history window and marks whether each visible call currently applies to the signed-in viewer's library.

Automatic detected-game prompts open the same Discord call-to-play wizard, with the detected game and immediate start preset. Title, audience, duration, note, and voice setup remain available. Automatic drafts are saved separately from manual drafts for 24 hours. While bot message actions are processing, the selected control shows "Working..." and action controls remain disabled until processing finishes.

## Discord

1. When a call to play matches someone who should be notified and that user has a linked Discord account, the bot can DM them directly. If someone becomes newly eligible later because they add overlapping library games while the call is still active, the app backfills the missing call notification for them as well. Quick response buttons in Discord are only active in the gateway-owning environment.
2. If a notified recipient responds from Discord, the creator and every other invited recipient who has not passed (including invitees who have not answered yet) sees it in their per-call updates-log DM: a single message per recipient listing every live update (interest, passes, running late, voice joins, game launches) newest-first with per-line timestamps in the recipient's timezone, rendered as pure plain text, and deleted and re-sent on each new event so Discord raises a fresh notification. Invitees who have not responded also get a call-to-action line in that log pointing back at their invite buttons, and choosing Can't make it is what stops those update pings for them. Passes always reach the creator and every other non-passed recipient, on every audience scope, so nobody has to guess who dropped out. A recipient who said they can't make it can still switch to interested later. Once interested, a recipient can also flag I'll be late (from the web app or the Discord invite); that notifies the creator and every other non-passed recipient and lists them separately from on-time interest in the call summaries. The original recipient invite stays in place and updates its buttons to match the current choice; instead of sending a separate confirmation DM, the pressed button briefly shows a confirmation ("You're in!", "Got it", or "Running late") before settling back to the updated invite. When the call uses a temporary Discord space, the invite itself carries link buttons for interested recipients: recipients already in the server get Text channel and Voice channel buttons, while everyone else gets a Join Discord invite button in their place. Recipients who already have an overlapping active call to play are still filtered out before those call notifications are sent.
3. Calls to play can optionally request a temporary Discord space in the Game's Up Discord server. That space provisions a dedicated private category with paired text and voice channels. Share its Discord invite to grant access to either new or existing server members, including people outside the call's audience. Direct channel links require access first. Ordinary invites created inside Discord need the temporary space's role selected under Edit invite link > Roles to grant access. The bot needs Manage Roles permission and must sit above the temporary role. Background cleanup replaces older server-only invites with role-granting invites and refreshes tracked call summaries; previously shared invite URLs must be shared again using the replacement. Creators can delete the retained space early after the call ends.
4. Users can leave a Play page setting on by default so the gateway-owning bot can DM them after it sees them start a game and offer to create a call to play straight from Discord. Those prompts only go out when there is no overlapping active call already, at least one person in the user's network with a matching game in their library could receive it, and the same game has not already prompted that user in the last 10 minutes.
5. Unanswered Discord call-to-play invites and auto-play prompts are edited in place when they go stale, so users see that the session ended or the observed game activity stopped instead of keeping an outdated call to action. Manual call-to-play endings and clears instead replace audience DMs with a fresh ended-summary message so Discord sends a new notification, and retained ended summaries can expose an `Archive` action when interactive Discord buttons are available. The creator's ended summary keeps the richer call details, including who was interested and the temporary Discord channel links, until the space is deleted.
6. Scheduled calls to play still notify the target audience immediately when created. At start time, the creator gets a check-in prompt to confirm whether the plan is still on.
7. If the creator confirms, users who already accepted get a go-time update and users who never answered get one follow-up reminder. Those go-time DMs stay actionable: accepted recipients can back out with a `No longer interested` action or flag `I'll be late`, unanswered recipients still get the normal `I'm interested` and `Can't make it` actions, the messages include the current interested count and interested-user list where relevant, and they still skip recipients who already declined or muted that creator. The creator check-in prompt itself stays in place with its buttons removed, and the confirm or end acknowledgement is sent as a separate update tied back to that call's summary DM.
8. When a call to play is created, the creator also gets a persistent Discord DM summary. Major lifecycle updates can still replace that DM with a fresh message so Discord emits a notification, but audience response updates edit the existing summary in place because the creator also receives the consolidated per-call updates-log DM. Those creator-facing update DMs reply to the tracked summary message when possible so concurrent calls stay visually separated in Discord. Quiet expiry or archive cleanup also falls back to edit-in-place behavior, and expired retained summaries can switch to an archive action for the creator. In the gateway-owning environment, active summaries still include a creator-only `End call to play` button.
9. For active single-game calls to play, the gateway-owning bot sends one launch alert when the creator starts that game and one launch alert to the creator each time an already-interested audience member initially starts it. Those alerts are one-time per active call and reset when the call changes.
10. Call-to-play DMs use natural local time phrasing such as `Friday Apr 17th at 10pm, for 2 hours` instead of raw timezone-abbreviation ranges. Right-now calls phrase their window as `For 2 hours starting now` so the duration and start are both explicit.
11. Admin users can inspect the DM lifecycle simulator from the debug surface to rehearse call-to-play and auto-play prompt flows locally without touching live Discord rows.
12. Structured Discord DMs prefer embed layouts where that feels natural, and the debug view keeps read-only DM previews for prompt and notification rows so admin inspection stays aligned with the live bot output.
13. The Play composer uses a step-based wizard that shows one section at a time for basics, audience, timing, and details instead of a separate self-only test posting path. The in-app detail view shows a "Can't make it" group alongside interested and running-late players: always for the creator of the call, and for everyone else on friend-targeted calls.
14. Bot-authored Discord DMs tied to tracked call-to-play and auto-play flows participate in retention cleanup. Call-to-play threads are shown as ended in place when their window closes, and the entire chain (creator summary, recipient invites, and dangling replies) is then deleted automatically 12 hours after the window ends. Creators and recipients can still archive or clean up sooner via the explicit actions.
15. In the gateway-owning environment, linked users can also send the bot DM commands for lightweight control without reopening the app: `help`, `status`, `end`, `autoplay`, and `cleanup`. `status` reports the latest active call to play, `end` clears any active calls to play, and `cleanup` removes older bot-authored DM clutter in that thread while preserving still-active tracked bot messages.
16. In that same gateway-owning environment, the bot also registers slash commands for adoption flows: the guild-only `invite-user`, `invite-link`, `app-members`, `server-ctps`, and `setup-ctp-post`, plus `post-ctp` which also works in the bot's DMs.
17. Discord invite links open a dedicated invite landing page, preserve server and inviter context through Discord OAuth, and can attribute a first accepted sign-in back to the originating Discord invite.
18. Admin debug includes an invite-attribution section so recent accepted invite flows can be verified without querying the database directly.
19. The Play view keeps recently ended calls to play visible as ended cards, shows whether each call currently applies to your library, and lets the viewer switch between 1 day, 1 week, and 1 month history windows.
20. Calls to play also have dedicated `/play/:playIntentId` detail pages. Discord DMs can deep-link straight into a specific call, Play cards expose a `Details` action, and legacy library-wide calls still expand the actual game options on that page so recipients can review what overlaps are in scope before they respond.
21. Discovery-based play-intent visibility can include both explicit friends and users from the Discord servers you opted into discovery.
22. Discovery remains based on opted-in shared Discord servers plus explicit in-app friendships. The Discord friend-list import path has been removed.
23. Discord is the only sign-in path.
24. Steam can be linked as a secondary account for library import only. It does not replace Discord auth or discovery.
25. Linked-account flows like Discord sign-in and Steam linking return directly to the current web URL after the provider callback completes.
26. Call-to-play DMs include a clickable creator Discord mention when available.
27. Subset call-to-play DMs can include game art for small selected-game sets: single-game calls show the chosen cover directly, and small multi-game sets show a lead cover with a short title list.
28. Signed-in web sessions subscribe to an authenticated dashboard SSE stream so open tabs refresh automatically after impactful changes such as play-intent updates, library edits, friend changes, Discord server selection changes, and linked-account or profile updates.
29. Calls to play can be composed entirely inside Discord through the same Basics / Audience / Timing / Details wizard as the web composer, rendered as a private step-by-step message. Entry points are the "Send out a call to play" button in the persistent Game's Up hub that a server admin places with `/setup-ctp-post` (its optional `lock-channel` flag stops members from sending messages in that channel so the button is not buried, and `lock-channel: false` reopens it), and the `/post-ctp` slash command in servers or bot DMs. Drafts resume for 24 hours, scheduled times are typed in the user's Game's Up timezone (e.g. `8pm`, `tomorrow 19:00`, `in 45m`), posting goes through the exact same play-intent service and validation as the app, and unlinked users who press the button get the invite landing link with server context instead. The review step shows missing selections in a red error embed above the summary and keeps Post disabled until they are resolved; posting errors use the same red error treatment.

## Steam import

1. Sign in with Discord first, open the Library tab, then use the Add games from Steam button to connect Steam and preview owned games.
2. Steam import respects the existing library model: the app shows a picker first and only imports the titles the user selects.
3. Steam import normalizes punctuation, trademark markers, and similar storefront-only title differences before matching against existing catalog games, so reused RAWG-backed games can keep the Steam source plus the original Steam spelling as an alias.
4. The same normalized-title matching is also used when the app records Discord-observed activity, and API startup repairs previously split duplicate game rows that only differ by storefront-only title decoration such as trademark symbols.
5. Steam may return no importable games when the account's game details are private or effectively unavailable to the API, so manual add should remain the fallback.
6. The picker can filter by library state and playtime, and sort by most played, least played, or recently played. Playtime comes from the Steam preview response and is not persisted at import time, so these controls only apply while the picker is open. The default "Recommended order" keeps the API ordering and pushes single-player-only titles to the end of each page as their metadata loads.

## Game catalog

Library entries store one canonical game with one or more selected platform flags, instead of requiring one separate library row per platform.

When the Discord presence bot sees a user playing a game in a shared server, the API keeps a lossy observed-game history and uses it to suggest likely library additions above the library grid. In local development, signed-in accounts with no personal observed history yet fall back to the seeded sample observations so the suggestion row can still be reviewed.

Users can also set one profile-level "when do you usually play" note and let individual games inherit it, while still attaching a game-specific schedule override when a title tends to happen at a different time.
